## 2026-08-11 · 클론만으로는 실행되지 않았다

원래 상태를 확인하는 것부터 시작했다.

- `docker-compose.yml`이 없었다. README에는 "Docker Compose로 전체 스택 실행 (추천)"이라고
  적혀 있고 그 아래에 `cd C:\springboot\node-js`라는 **개발자 로컬 절대경로**가 남아 있었다.
  남이 클론하면 실행할 방법이 없었다.
- `.env.example`이 없어 필요한 환경변수를 알 수 없었다.
- `package.json`은 `UNLICENSED`인데 README는 MIT였다.
- IDE 설정(`.iml`)과 AI 도구 로컬 설정이 추적되고 있었다.
- 실질 테스트가 0개였다. `app.controller.spec.ts`는 NestJS가 생성한 기본 파일이다.

`TypeORM`의 `synchronize`와 `logging`이 코드에 `true`로 박혀 있었다.
`logging: true`는 쿼리마다 콘솔 출력이 나가므로, 이 상태로 성능을 재면
측정값이 의미를 잃는다. 둘 다 환경변수로 분리했다.

## 2026-08-11 · 마지막 1개 쿠폰이 사라지고 있었다

부하 시나리오를 설계하려고 발급 경로를 읽다가 발견했다.

Lua 스크립트가 **단일 정수**에 상태와 값을 함께 실어 반환하고 있었다.

| 반환값 | 의미 |
|---|---|
| `-1` | 중복 발급 |
| `0` | 재고 소진 |
| 그 외 | 성공 (값은 발급 후 잔여 수량) |

재고가 1개 남았을 때 발급하면 `remaining - 1 == 0`이 된다.
그런데 호출부는 `0`을 재고 소진으로 읽는다.

```ts
if (result === -1) return { status: 'DUPLICATED' };
if (result === 0) return { status: 'SOLD_OUT' };   // 마지막 1개가 여기로 샌다
```

그 결과:

1. Redis에서는 재고가 차감되고 발급 이력 키까지 설정된다
2. 호출부는 `SOLD_OUT`으로 판단해 DB에 기록하지 않는다
3. 해당 사용자는 발급 이력 때문에 재시도해도 `DUPLICATED`로 막힌다

**100개 한정 쿠폰마다 1개가 증발하고, 한 명은 받지도 못하면서 차단됐다.**

sentinel 값과 유효 값의 도메인이 겹친 것이 원인이므로 상태와 값을 분리했다.
`[code, remaining]`을 반환하고, `code`가 성공이면 `remaining`이 0이든 상관없이 성공이다.

### 확인

옛 스크립트를 재현용으로 보관해 같은 조건에서 비교했다
(`npm run check:lua` 시나리오 5).

| 재고 100개 / 1,000명 동시 | 수정 전 | 수정 후 |
|---|---|---|
| 사용자에게 발급 성공 | 99 | **100** |
| 실제 차감된 재고 | 100 | 100 |
| 누락 | **1** | **0** |

Lua 본문은 별도 모듈(`src/redis/issue-coupon.script.ts`)로 분리했다.
검증 스크립트가 복사본을 쓰면 한쪽만 고쳤을 때 검증이 무의미해진다.

## 2026-08-11 · 부하 테스트가 부하를 걸지 않고 있었다

k6 첫 실행에서 3,000건 중 **2,934건이 `DUPLICATED`**로 튕겼다.

사용자를 이렇게 골랐던 것이 원인이다.

```js
const index = (__VU - 1) * 100000 + __ITER;
const userId = seed.userIds[index % seed.userIds.length];
```

`100000 % 3000 == 1000`이라 VU 1·4·7…이 같은 구간을 집는다.
실제로는 **66명만 발급을 시도했다.** 부하가 걸린 것이 아니었다.

`exec.scenario.iterationInTest`(시나리오 전체에서 고유하게 증가하는 인덱스)로 교체했다.

> 부하 테스트 스크립트 자체도 검증 대상이다. 숫자가 나왔다고 해서
> 의도한 부하가 걸린 것은 아니다.

## 2026-08-11 · 꼬리 지연을 쫓다가 가설 세 개가 틀렸다

### 가설 1 — 커넥션 풀이 부족하다 → 틀림

발급 요청 하나당 DB를 두 번 친다(`쿠폰 조회` → `사용자 조회` → Redis).
`pg` 기본 풀은 10인데 동시 요청이 200개니 대기가 생길 것이라 봤다.

50으로 늘려 측정했다.

| | pool=10 | pool=50 |
|---|---|---|
| p50 | 187 ms | 141 ms |
| p95 | 353 ms | 610 ms |
| **p99** | **1,110 ms** | **2,780 ms** |

중앙값은 나아졌지만 꼬리가 2.5배 악화됐다.

대기가 사라진 것이 아니라 **옮겨간 것**이다. 앱에서 순서대로 기다리던 것이
PostgreSQL 안에서 커넥션끼리 경합하는 형태가 된다. PostgreSQL은 커넥션당
프로세스이므로 동시 커넥션이 늘수록 컨텍스트 스위칭과 락 경합이 커진다.

조정은 가능하게 두되(`DB_POOL_MAX`) 기본값 10을 유지하기로 했다.

### 가설 2 — 쿠폰 조회가 병목이다 → 부분적으로만 맞음

발급 기간은 거의 바뀌지 않으므로 Redis에 캐시하고 미스일 때만 DB를 읽게 했다.
캐시는 쿠폰 생성·수정·삭제·동기화 시점에 갱신한다.

| | 캐시 전 | 캐시 후 |
|---|---|---|
| 처리량 | 806 req/s | **915 req/s** |
| p50 | 187 ms | **156 ms** |
| p99 | 1,110 ms | 1,130 ms |

처리량과 중앙값은 개선됐지만 **꼬리는 그대로였다.**

### 가설 3 — 비동기 INSERT가 병목이다 → 틀림

발급 성공 시 DB INSERT가 비동기로 1,000건 발생한다. 이것이 커넥션을 물고
있을 것이라 보고, 재고를 1로 두어 INSERT가 1건만 나도록 만들어 비교했다.

| | 재고 1,000 | 재고 1 |
|---|---|---|
| 처리량 | 915 req/s | 1,117 req/s |
| p50 | 156 ms | 129 ms |
| **p99** | 1,130 ms | **1,640 ms** |

INSERT를 없앴는데 꼬리는 오히려 나빠졌다.

### 실제 원인 — 부하 모델

세 가설이 모두 빗나갔다면 서버가 아니라 **재는 방식**을 의심해야 한다.

`shared-iterations`는 VU가 응답을 받는 즉시 다음 요청을 보내는 **닫힌 모델**이다.
200개 VU가 쉬지 않고 때리면 서버는 포화 상태가 되고, 그때의 p99는
처리 속도가 아니라 **대기열 길이**를 재는 것이 된다.

도착률을 제어하는 열린 모델(`constant-arrival-rate`)로 다시 쟀다.
**같은 서버, 같은 코드다.**

| | 닫힌 모델 (VU 200) | 열린 모델 (300/s) |
|---|---|---|
| p50 | 156 ms | 2.47 ms |
| **p99** | **1,130 ms** | **4.62 ms** |

220배 차이다. p99 1초는 서버의 문제가 아니었다.

### 실제 용량

| 도착률 | 실제 처리 | p50 | p95 | p99 | 드롭 |
|---|---|---|---|---|---|
| 300/s | 299/s | 2.47 ms | 3.35 ms | **4.62 ms** | 0 |
| 600/s | 598/s | 3.67 ms | 27.6 ms | **51.2 ms** | 0 |
| 900/s | 759/s | 498 ms | 798 ms | 893 ms | 3,535 |

600 req/s까지 여유롭고, 900에서 포화된다. 실질 상한은 약 **760 req/s**.

> **닫힌 모델은 정합성 검증에, 열린 모델은 지연·용량 측정에 쓴다.**
> 포화 상태에서 잰 p99를 성능 지표로 보고하면 틀린 숫자를 말하게 된다.

## 2026-08-11 · 배포 구성을 분리했다

기본 `docker-compose.yml`은 PostgreSQL(5432)과 Redis(6379)를 모든 인터페이스에
열어둔다. 로컬에서는 편하지만 공인 IP가 붙은 서버에 그대로 올리면
**인증 없는 Redis가 공개망에 노출**된다.

`docker-compose.prod.yml` 오버라이드에서 DB/Redis 포트를 닫고, API는 루프백에만
바인딩하고(외부 노출과 TLS는 Nginx가 담당), Redis에 `requirepass`를 걸었다.
`DB_PASSWORD`·`REDIS_PASSWORD`·`CORS_ORIGIN` 중 하나라도 비어 있으면 기동하지 않는다.
안전하지 않은 설정이 실수로 배포되는 것보다 아예 뜨지 않는 편이 낫다.

이를 위해 애플리케이션도 열어야 했다. `RedisService`가 host/port만 받고 있어
`requirepass`를 걸면 접속하지 못했고, CORS는 `origin: true`로 전체 허용이었다.

포트 오버라이드에는 `!override`를 쓴다. `!reset`은 값을 비우므로
호스트의 Nginx가 API에 접근할 수 없게 된다.

## 남은 문제

우선순위 순.

### 1. 인증이 없다

`/api/admin/coupons` 계열에 인증·인가가 전혀 없다.
`admin` 경로인데 누구나 쿠폰을 생성하고, body에 `userId`만 넣으면
남의 계정으로 발급할 수 있다. **현재 상태는 데모다.**

### 2. DB 기록이 fire-and-forget이다

```ts
this.issuedCouponsService.createIssuedCoupon(...)
    .catch((error) => console.error(...));   // 로그만 남고 유실
```

저장이 실패하면 사용자는 성공 응답을 받고도 쿠폰을 갖지 못하며,
재시도하면 발급 이력 때문에 차단된다. 복구할 방법이 없다.

아웃박스 패턴이나 큐 기반 기록으로 가야 재시도·DLQ가 가능해진다.
Redis는 **상태**("지금 몇 개 남았나")를, 큐는 **이벤트**("누가 받았다")를
맡는 구조가 이 규모의 표준이다.

### 3. 발급 이력 TTL이 86400초로 고정이다

쿠폰 기간이 24시간보다 길면 이력이 먼저 만료되어 같은 사용자의 재발급이
Redis를 통과한다. 재고는 차감되고 DB `UNIQUE` 제약이 INSERT를 막지만,
그 예외는 2번의 `catch`에서 사라진다. **재고만 조용히 준다.**

TTL을 `coupon.endAt` 기준으로 넘기면 닫힌다. 파라미터는 이미 열어 두었다.
`npm run check:lua` 시나리오 4가 TTL을 1초로 축소해 이 경로를 재현한다.

### 4. `syncRedisFromDatabase()`가 상황을 악화시킬 수 있다

`remaining = totalQuantity - issuedCount(DB)`로 되돌리므로, 2·3번으로 누락된
만큼 재고가 되살아난다. 그런데 그 사용자들의 발급 이력은 Redis에 남아 있어
그들은 여전히 받지 못한다. 총량은 맞지만 **받았어야 할 사람이 못 받는다.**

### 5. Redis가 단일 인스턴스다

장애 시 재고 카운터를 잃는다. AOF를 켜 두었으나 복제·failover는 없다.
